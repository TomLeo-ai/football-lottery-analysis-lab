# v0.2.0 Release Candidate Notes

## Status

This document describes implemented `v0.2.0` release-candidate scope and the
evidence required for a release decision. It is **not a release/adoption
claim**. Its presence does not create a `v0.2.0` tag or GitHub Release, prove
external use, Stars, Forks, Issues, contributions, or adoption, or indicate
approval for Codex for Open Source.

The repository remains non-official and simulation-only. It does not sell
lottery products, place wagers, process payments, proxy purchases, or promise
accuracy or profit.

## Implemented candidate capabilities

- Real Tesseract.js 7.0.0 OCR runs in desktop Chromium from packaged,
  same-origin worker, WebAssembly, and `eng`/`chi_sim` trained-data assets.
- Crop, rotation, redaction, and recognition happen locally. Original image
  pixels and complete OCR text remain in transient browser memory and are not
  sent to the backend or written to persistent browser/server storage.
- The browser sends only the minimum editable `OCR_CANDIDATE_V2` structured
  candidate. The candidate path supports WDL markets only.
- Review drafts are persisted with ordered matches and markets, a revision, and
  compare-and-swap updates. The same workflow URL restores an active draft
  after page reload and backend process restart.
- Explicit confirmation produces a server-authoritative snapshot bound to the
  confirmed revision. Analysis and saved plans are generated from that
  authority lineage; clients cannot assert report, snapshot, or plan authority.
- UUID idempotency keys protect workflow, OCR candidate, draft, confirmation,
  analysis, and plan mutations. Reusing a key with a different payload is
  rejected.
- A direct saved-plan link restores the resulting simulated plan. The default
  proof uses `MOCK_RULE_ENGINE`; optional LLM output remains advisory and cannot
  replace the rule-engine authority.

## Internal API breaking change

The revisioned OCR workflow intentionally replaces the previous confirmation
write contract:

```text
POST /api/ocr/workflows
GET  /api/ocr/workflows/{workflowId}
POST /api/ocr/workflows/{workflowId}/ocr-candidates
GET  /api/ocr/review-drafts/{ocrTaskId}
PUT  /api/ocr/review-drafts/{ocrTaskId}
POST /api/ocr/review-drafts/{ocrTaskId}/confirm
```

Mutating calls require a UUID `Idempotency-Key`; draft updates and confirmation
also carry the expected revision. Clients must reload the current active draft
after a revision conflict and must not retry with a different payload under the
same key.

The former `POST /api/ocr/review/confirm` route now returns `410 Gone` with
`LEGACY_CONFIRM_ENDPOINT_REMOVED`. It is a deliberate tombstone, not a
supported compatibility write path.

## Database migration and legacy compatibility

Flyway V3 introduces `ocr_workflow`, `workflow_operation`, and
`ocr_review_draft`, plus workflow, authority, provenance, schema, and confirmed-
revision columns across the authority chain. V4 adds persisted analysis output
and authority revision/snapshot fields.

The added authority columns are nullable for existing Stage 8 rows. This
**legacy null compatibility** preserves historical reads and avoids fabricating
lineage that old data never had. New Stage 9 writes are stricter: missing legacy
parents or incomplete authority lineage are rejected and are not silently
upgraded.

Before upgrading a local database:

1. Stop the backend and back up `apps/server/data/`.
2. Start the `0.2.0` candidate so Flyway applies the additive migrations.
3. Keep old records read-only unless they already contain valid Stage 9
   authority; create a new workflow for new writes.
4. Update internal clients to the revisioned endpoints and UUID idempotency
   contract before removing any local fallback code.

## Verification contract

Run against the exact candidate commit:

```shell
npm ci
npm run verify:stage9
npm audit --json
npm audit --omit=dev --json
```

`verify:stage9` is the current release-readiness gate. It covers community and
compliance checks, the third-party OCR inventory and packaged assets, OCR Core,
Web typecheck/tests/build, Maven verification, the historical Stage 8 smoke,
and the private real Stage 9 Chromium golden flow. `verify:stage8` is retained
only for historical reproduction and is not the current release gate.

The Stage 9 flow uses a test-owned temporary H2 database and the same built JAR
before and after backend restart. It rejects non-same-origin browser traffic and
checks browser storage, backend/network metadata, logs, build output, temporary
files, and the closed database for prohibited original-image or complete-raw-
text persistence. It does not capture screenshots, video, or traces.

The OCR component inventory, licenses, source references, and checksums are
documented in [`../third-party-ocr.md`](../third-party-ocr.md) and
[`../../third_party/ocr/manifest.json`](../../third_party/ocr/manifest.json).
Those records document provenance and redistribution obligations; they are not
legal clearance or a grant of rights in third-party data, models, or trademarks.

## Known limitations

- Local, single-user research use only; multi-user authentication, tenant
  isolation, production operations, and distributed concurrency are outside
  this candidate.
- The golden browser proof targets desktop Chromium. Other browsers are not
  certified by this gate.
- The trustworthy screenshot path accepts the documented fictional fixture and
  WDL markets only; it does not authorize uploading or redistributing third-
  party screenshots.
- OCR quality depends on image quality and language data. Human editing and
  explicit confirmation remain mandatory.
- Optional OpenAI-compatible providers require a backend-only credential and
  are outside the no-key Stage 9 golden path.
- Stage 9's temporary database proves isolated migration/restart/privacy
  behavior; it is not a production deployment or load test.
